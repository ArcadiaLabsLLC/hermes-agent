## 2. The two remote rows — one design: a brain repo and a personal realm repo

### 2.1 What is true today (file::symbol)

- **The default brain** is a git repo at `paths.default_brain_dir(ws)` with one commit under
  `default_brain.IDENTITY_PAIRS(machine)`, a machine-local binding `board.binding_path(ws)` (`{slot, path,
  brain_dir, default_branch, created_at, machine, remote_url: None, retired_into}`), listed as slot `brain`
  by `board.default_board` (`local=True`, `clone_url=remote_url`). `default_brain.promote_default_brain`
  refuses `not_built`. `work/service.py::_default_brain_state` calls `ensure_default_brain` from
  `capabilities` and `store.normalize_default_brain` moves its rows into `board.first_repo_brain` once a repo
  brain is bound (one `APPEND`, one `DELETE`, `retire_binding`).
- **The Work writer** (`work_store/writer.py::Writer`) pushes `work/<machine>:<default_branch>` with plain
  `git_cmd.run_git` — no credential door; a local board skips fetch and push (`Writer._push`); the batch lane
  git (`batch/lane_git.py::LaneGit`, `Clone.local`) is the same shape.
- **Slots:** `workspace_slots.declare` REPLACES the set (names missing are tombstoned);
  `normalize_declaration` has the `repo.local` arm; `require_publish_right(ws, credential)` passes a
  no-realm workspace and a server-less realm (the allow stub) and fails closed on a server-bound realm
  without the launcher-brokered credential; `workspace_slot_setup.clone_slot` refuses a local slot
  (`slot_local_only`) and clones as a background terminal row; `bind` writes the machine root.
- **The GitHub token chain** (upstream, `hermes_cli/git_credentials.py`): `iter_git_basic_auth(url)` yields
  `(source, (username, password))` from `GITHUB_TOKEN`/`GH_TOKEN`, `gh auth token`, then the machine's
  `git credential fill`; `with_git_auth(env, url, auth)` renders a one-shot `http.<origin>/.extraheader` into
  `GIT_CONFIG_*` env; `hermes_cli/github_api.py::github_token` is the same ladder for REST calls.
- **Realm sync:** `realm_sync/git.py::_sync_repo_path` keys every local realm's repo at
  `realm_sync_root()/local` (a remote `sync_manifest_ref` does not move it); `_ensure_sync_repo` CLONES only
  when the repo does not exist and `sync_manifest_ref` looks remote, else `git init` — an existing repo never
  gains a remote; `publish._stage_commit_and_push` runs a bare `git push` (needs an upstream);
  `pull_realm_sync` runs `pull --ff-only` only when `_has_remote`. `realm_membership.RealmSyncCredential`
  parses the frozen JSON (`realm_id`, `git_url`, `git_authorization`, …); `CredentialSubject.LOCAL_REALM` is
  `realm_id = "local:<id>"`, `admits_realm` matches a server-less realm by id, `has_backend_realm` is False
  (no publish notify); `adopt_realms` sets `sync_manifest_ref` from a SERVER realm's `git_url` — the local
  twin of that line is what the row asks for. Backend `docs/architecture/02-realms-nexus.md` §4c: one
  personal repo per PLAYER, a subtree per local realm, credential from `POST /api/me/realms/local:<id>/
  sync/credential`, git scope always WRITE; §4 "`GitHubProvider.ensure_repo` verifies, never creates" — the
  App cannot create repos. Launcher `lib/features/mission_control/sync/realm_sync_api.dart::
  RealmSyncBackendApi.fetchSyncCredential(realmId)` posts `realms/{id}/sync/credential` (server realms only).

### 2.2 Decisions

- **Which account counts as connected** (owner decision §7, recommended path): the upstream chain, because
  the Work writer and the batch lane push through the machine's own git auth and nothing else: a remote
  made with a credential the machine's git cannot present is a remote the writer cannot reach. The realm
  git-host binding is App-brokered, short-TTL (900 s), launcher-held, and cannot create a repo (backend
  §4c); it is the LOCAL-REALM lane (§2.6), where the credential rides every git call as `-c`. A writer
  credential door is a later row (`RT-WORK-WRITER-CREDENTIAL-DOOR`, §8), not this one.
  `Decided (plan):` "connected" = `git_host_account.connected_github()` returns an account: some
  credential of `iter_git_basic_auth("https://github.com")` answers `GET https://api.github.com/user` 200,
  and the login is the repo owner. GitHub only in this cut (sources 1–2 are GitHub-only; source 3 may
  name another host but no host API is wired: `git_host_unsupported`).
- **Repo name and visibility:** `eternia-work-<workspace slug>` (`Workspace.slug`, else
  `safe_path_token(workspace_id)`), PRIVATE, `auto_init: false`. A name that exists already (GitHub 422)
  refuses `remote_exists` and is never adopted — adopting a repo hermes did not make could push a brain into
  someone's project; the operator declares it by hand if that is what they want.
- **Who declares in a server-bound realm:** hermes writes the declaration itself when
  `require_publish_right(ws, None)` passes (no realm, server-less realm); in a server-bound realm it STAGES
  the declaration in the binding (`declaration: {"state": "pending", "slot": <entry>}`), `capabilities`
  answers `remote_pending_declare` with the entry, and the Launcher's next credentialed `slots.declare`
  includes it (launcher row `MC-WORK-BRAIN-REMOTE`, §8). Consistent with `RT-WORK-DEFAULT-BRAIN-REALM`'s
  recommendation (the operator's click carries the credential).
- **Second machine:** adoption is by the declared slot. Before creating a default brain,
  `ensure_default_brain` looks for a live declared `brain` slot with a `clone_url`; one that is unbound
  here is cloned synchronously into `paths.default_brain_dir(ws)` (or `…/brain-remote` when a local brain
  already stands there) through the shared adopter, bound, and listed as a repo brain; a local brain's rows
  then move in through `normalize_default_brain` (its target `first_repo_brain` finds slot `brain`). A
  no-realm workspace's declaration never syncs; there the operator declares the slot (the Launcher shows the
  remote URL to copy, §8).
- **Local realm adoption:** the credential's `git_url` becomes `sync_manifest_ref` (mirror of
  `adopt_realms`) AND `origin` of the existing shared repo, in the same call, from every sync verb.
- **First push into an empty personal repo:** the shared adopter sets the upstream (`push -u` when the
  remote is empty and local has commits; `branch --set-upstream-to` after a fetch); publish's push becomes
  `push -u origin HEAD` when `@{u}` is unset (one additive branch in `_stage_commit_and_push`).
- **A personal repo that already carries other machines' subtrees** (two machines, one player): local
  `realm_sync_root()/local` has its own commits, origin has unrelated ones. `Decided (plan):` merge
  `--allow-unrelated-histories` only when the two tips touch no common path except `.gitattributes`
  (ours wins there; both are the managed file); any common path refuses `sync_remote_diverged` with the
  paths in `safe_details`. The brain adopter never merges (a brain repo is created by this lane, so the
  remote is empty or the local dir is).

### 2.3 Stage R0 — the shared adopter `agent_runtime/git_remote_adopt.py` (new, `stores`)

```python
class Adoption(StrEnum): ADDED_PUSHED | ADDED_FETCHED | ALREADY | MERGED_UNRELATED
@dataclass(frozen=True) class AdoptReceipt: outcome: Adoption; url: str; branch: str; head: str; detail: str = ""
class AdoptRefused(ValueError): reason: str   # url_mismatch | remote_diverged | fetch_failed | push_failed | not_a_repo
def adopt_remote(repo: Path, url: str, *, branch: str = "main", config: Sequence[str] = (),
                 merge_unrelated_if_disjoint: bool = False, run=run_git) -> AdoptReceipt
```

Steps, each one `run_git` call with `config` as `-c` pairs (a credential never touches `.git/config`):
`remote get-url origin` → present and equal → `ALREADY` (after a `fetch`; upstream set if unset); present
and different → `url_mismatch`; absent → `remote add origin <url>`; `fetch origin <branch>` (a remote with
no such branch is "empty": `couldn't find remote ref`); local has no commits (`rev-parse --verify HEAD`
fails) and remote has → `reset --hard origin/<branch>` + `branch --set-upstream-to` → `ADDED_FETCHED`;
local has commits and remote empty → `push -u origin HEAD:<branch>` → `ADDED_PUSHED`; both have commits:
`merge-base` exists → `ALREADY` (upstream set); none → with `merge_unrelated_if_disjoint` and
`diff --name-only <tip-A> <tip-B>` sharing no path but `.gitattributes` → `merge --allow-unrelated-histories
--no-edit -X ours origin/<branch>` → `MERGED_UNRELATED`, else `remote_diverged`. Stderr is scrubbed with
`realm_sync.git._scrub_config_values` before it reaches a receipt. Receipt `git.remote_adopted {repo
(basename), outcome, branch}` through `work_store.receipts.emit`.

Tests `tests/agent_runtime/test_git_remote_adopt.py` (real `git` in `tmp_path`, a bare `origin.git`):
`test_empty_remote_gets_the_local_history_pushed_with_upstream` (`ADDED_PUSHED`; `rev-parse @{u}` works);
`test_empty_local_takes_the_remote` (`ADDED_FETCHED`); `test_same_url_is_already_and_still_fetches`;
`test_a_different_origin_refuses_url_mismatch`; `test_unrelated_histories_merge_only_when_paths_are_disjoint`
(two cases: disjoint `realms/a/`, `realms/b/` → `MERGED_UNRELATED`; a shared `README.md` → `remote_diverged`);
`test_config_pairs_never_land_in_git_config` (a fake `http.extraHeader=Authorization: x` pair; `.git/config`
has no `extraheader`); `test_stderr_is_scrubbed` (the pair's value absent from the refusal's detail).
Killing mutations: adopter writes `git config remote.origin.url` via `config` instead of `remote add` → fine,
but writes the `-c` pair with `git config` → `test_config_pairs_never_land…` red; merge without the disjoint
check → `remote_diverged` case red; `push` without `-u` → upstream case red.

### 2.4 Stage A1 — the GitHub door `agent_runtime/git_host_account.py` (new, `stores`)

- `GitHubAccount(login: str, source: str)`; `connected_github(timeout=10.0) -> GitHubAccount | None`:
  for each `(source, auth)` of `hermes_cli.git_credentials.iter_git_basic_auth("https://github.com")`,

  else `host_unreachable`. The token never reaches a log line (`github_api`'s rule).

  `REMOTE_EXISTS="remote_exists"`, `GIT_HOST_UNSUPPORTED="git_host_unsupported"`, `TOKEN_SCOPE="token_scope"`,

## 4. `RT-ETERNIA-SKILLS-LENDS-SKILLS` — lending skills to a Work task or a worker

### 4.1 What is true today

`agent_runtime/conversations/worker_skills.py::install` registers `eternia.skills.{list,detail,history}` on the
tui gateway `server` with `InspectParams(SessionParams) {skill_id}`; the read is the PARENT session's
(`session.activate` snapshot → `cwd`, `tools`; `skill_inspection_reader().catalog/detail`; history from
`state.db` by the session key). Children: `conversations/worker_subagents.py` methods carry `owner_scope`,
`worker_generation`, `child_ref` (`subagents/model.py::COMMAND_PARAMS`); `subagents/native.py::inspect_native`
resolves the owner session and `references.child(owner, record)` signs `(owner, token-of-record["agent"],
subagent_id, started_at)` — a `child_ref` resolves to a LIVE record whose `agent` is the child `AIAgent` and
whose `session_id` is the child's session. A child is built by upstream `tools/delegate_tool.py::_build_child_agent`
with the parent's toolsets minus the blocked ones; no skill set is passed, and the fork's compact-category seam
attribute (`chat_lane_skill_index.COMPACT_ATTR = "_chat_lane_compact_skill_categories"`, read by the one guarded
line in upstream `_skills_prompt`) is not copied to the child, so a child's index is unscoped (every category in
full). A persona turn can be handed skills for ONE turn: `chat_verbs/queue_skill.py::queue_skills_next_turn`
(resolves and compatibility-checks each, then `queued_skills.queue_skills_for_next_turn(persona_id, session_id,
skills)`), consumed by `mission_chat_turn_context` (`consume_queued_skills`) — the RPC `runtime.chat.queue_skill`.
An instance's standing set is `skill_overrides` (`runtime.agent.place`'s `skills`). Work: `executor.Assignment`
has no skill field; `persona_turn.PersonaTurnExecutor.start_from` builds the turn and enqueues it on the root;
`goal_turns.arm_run` forges continuations. The row grammar has `assignee:` as the one typed segment
(`work-on-markdown` §3.1, ADR 0011 amendment).

### 4.2 Decisions

- **Where the lent set is written.** `Decided (plan):` for a Work row, IN THE ROW: a segment
  `skills: `<slug>`[, `<slug>`]` (the `assignee:` twin — one home, synced by git, visible on every machine
  and on the launcher's board); `Assignment.skills` is derived from it by the engine and the planner and is
  never a second store. For a worker (no row exists), a lend record `<store_root>/skill_lends/<token>.json`
  `{target: "child:<subagent_id>", owner_session, skills, lent_at, lent_by}` written by the verb; it lives as
  long as the child (the sweep below drops it when the record is gone). The child's session is NOT the store:
  a session file is upstream's and a replaced worker (new generation) must not inherit a lend.
- **How the child reads it.** Two reads, both existing seams: (1) visibility — the lend's skills join the
  child's kept set through `COMPACT_ATTR` on `record["agent"]` (`compact_skill_categories(keep)` over the
  parent's kept set ∪ lent; a child with no scoped parent and no lend stays unscoped); (2) loading — a lend to
  a RUNNING child is announced by the existing `eternia.subagents.steer` text (`"Skills lent: <slugs>. Load
  one with skill_view(<id>) when it applies."`, ≤ 8 KiB); the child loads bodies itself, the same way a
  persona does. For a Work run the executor queues the row's skills for the run's turn through
  `queue_skills_for_next_turn` (bodies preloaded for that turn, as `runtime.chat.queue_skill` does) and
  `goal_turns` re-queues them for every `UNTIL_DONE` continuation.
- **The revoke.** `eternia.skills.lend` with `mode: "revoke"` (and `runtime.work.lend_skills` with
  `mode: "revoke"` for a row): the record is deleted / the segment removed, the attr recomputed, a steer
  `"Skills no longer lent: …"` sent; an already-loaded body cannot be unloaded mid-turn (stated in the reply:
  `effective: "next_turn"`).
- **The verb.** `eternia.skills.lend` is the gateway verb (session-addressed, the child half); the row half is
  the serve's `runtime.work.lend_skills` because the row's one writer is the serve's `Writer`
  (`Decided (plan):` a gateway worker never runs the writer; a client that holds a Work lease talks to the serve
  for the row). Both are write verbs (RULED).

## 5. `RT-LONG-CALL-WAKE-LOST-ON-RESTART` — the boot sweep

### 5.1 What is true today

A promoted call is a `running` row in `<background-work home>/tool_calls.json` (`long_tool_calls._running_row`:
`handle, tool_name, label, status, started_at, session_key, turn_id, tool_call_id, expires_at (24 h), pid,

`parent_session_id`, `handle`, `tool`, `outcome`, `elapsed_ms`, `result`); the drain owns it by

`boot_phases._boot_sweeps_and_ready_frame` (`repair_orphaned_chat_turns`, `restore_undelivered_dispatches`,

### 5.2 Decision

`Decided (plan):` on serve boot, every `running` row in every background-work home of this store root whose

`expires_at = now + _FINISHED_TTL_S`) and a `tool_call_finished` wake with `outcome = "lost"` and
`result = "The runtime restarted while this call ran; its result was never produced. Re-issue the call if
you still need it."` is queued. The drain delivers it like a finish (`format_tool_call_finished` already
renders `outcome`) and `note_wake_settled` retires the row. An unprovable pid (`PID_NO_BASELINE`,
`PID_START_TIME_UNREADABLE`) is left alone (the reader shows `unknown`, as today). The `lost` row persists
through a second restart before its wake is delivered: the sweep re-queues a wake for a `lost` row too (it is
idempotent: the drain's event key is `tool_call:<handle>`, a replay).
