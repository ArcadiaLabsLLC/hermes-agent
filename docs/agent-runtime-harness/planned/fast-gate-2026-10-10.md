## 1. The green-result cache

**Verdict: PLAN.** A test file is skipped when nothing it depends on has changed since its
last green run on this box, and the dependency set is RECORDED at run time, not inferred.

**Decision and why.** Two ways to know what a test file depends on: walk its imports
statically (`run_tests_bundled_scope.py::imported_modules` already does one level, for
selection) or record what the process actually touched. The static walk is the wrong
instrument for a cache key: it is one level deep (the conftest's own imports — `tests/_fixtures/*`,
`tests/_downstream/*` — are not the test file's), it cannot see
`importlib.import_module`, plugin loaders, data files, fixtures read by path, directory
listings or the config roots a test copies; and every miss is a FALSE GREEN. Recording is
exact for the process and over-approximates safely inside a bundle: CPython raises the
`import` audit event only on first load (verified on this box: a cached re-import raises
nothing), so a member's import set cannot be attributed exactly when an earlier member
already loaded the module. The record therefore attributes to each member what fired while
it ran AND the repo-rooted modules present in `sys.modules` when it finished — a superset,
so a change invalidates more than it must, never less (CLAUDE.md: over-approximation is the
safe direction). `open`, `os.listdir`, `os.scandir`, `glob.glob` and `subprocess.Popen`
raise on every call, so data files, listed directories and spawned children ARE attributed
exactly. A child process is the one true hole: its imports are its own. Stage 1 makes any
file that spawned a process depend on the whole tree (the ALL sentinel); stage 1b records
children through the runner's own `PYTHONPATH` and retires the sentinel where a record
arrives.

**The key.** `key(rel) = sha256` over, sorted, one line each:
- `path\t<blob>` for every recorded path under the repo root (modules by `__file__`, opened
  files, the test file itself), `<blob>` being the git blob id — from one `git ls-files -s`
  (20,567 entries, 0.46 s here) for tracked clean paths; for a path `git status --porcelain
  --untracked-files=all` names (modified or untracked), the blob id computed the git way
  (`sha1("blob <len>\0" + bytes)`), so committing a file does not change its key; a recorded
  path that no longer exists contributes `path\tMISSING`;
- `dir\t<sorted names>` for every listed directory under the repo root;
- `ALL\t<sha256 of the whole ls-files + dirty map, minus the excluded prefixes>` when the
  record says the file spawned a process and no child record covers it (Q1 names the
  exclusions; recommended: `Harness_Brain/`, `docs/`);
- the fixed inputs, once per run: `runner\t<sha of scripts/run_tests_bundled*.py,
  scripts/_bundle_plugin/*, scripts/run_tests_bundled.sh, scripts/run_tests.sh,
  scripts/_activation.sh, scripts/ensure_fork_dev_deps.py, scripts/test_*.txt,
  tests/fixtures/upstream_skip_list.txt, tests/fixtures/upstream_manifest.txt>`;
  `interp\t<sys.version, platform.platform(), sorted importlib.metadata distributions
  name==version, sha of uv.lock + pyproject.toml + requirements-fork-dev.txt>`;
  `env\t<sorted HERMES_TEST_* names and values present, TZ, LANG, PYTHONHASHSEED>`;
  `pytest\t<the passthrough pytest args>` (any passthrough arg — `-k`, `-m`, `-x`, `--lf` —
  disables the cache for reading AND writing: the result is not a whole-file green);
  `schema\t<CACHE_SCHEMA constant>`.
The conftest chain needs no rule of its own: `conftest.py`, `tests/conftest.py`, every
`tests/_downstream/*` and `tests/_fixtures/*` module and the id-marker tables are imported
by every process and so are recorded paths of every file; a marker-table change changes
every key, which is what "xfail/xpass-strict files whose marker table changed" requires.

**Never cached.** A file red, errored, flaky (red then green on retry), an isolation leak or
unreached in its bundle, killed by a timeout, re-run as a straggler; a file on
`scripts/test_idle_box_files.txt` or `tests/fixtures/upstream_skip_list.txt` (never
selected anyway); a file NAMED on the command line (named always runs, as the skip list's
O1); any file when a passthrough pytest arg is present; any file whose last green is older
than `--cache-max-age` (14 days, Q2). A written entry carries the key, the run id, the
seconds and the record id, so a hit prints `(cached, 0.0s; green <date>, <seconds>s)`.

**The audit.** Every run re-executes a random sample of its hits — `max(25, ceil(2 % ×
hits))`, drawn by `random.Random(seed)` with the seed printed and recorded — as ordinary
members. A sampled hit that comes back red is run once more alone: red again is a **cache
defect** (the key missed a dependency), printed as `=== ✗ CACHE AUDIT: N cached-green
file(s) red on re-execution ===` with the file, its recorded paths and the diff of the
tree since its green; the run exits 1 and bumps the store's generation (`generation` file;
every entry below it is a miss) so the next run is cold; the defect is filed on arrival. Green
alone is a flake, reported as today's FLAKY and never cached again until green twice.

**Where it lives.** `gate_store_dir(repo_root)` = `(plan.primary_checkout(repo_root) or
repo_root) / ".pytest_cache" / "hermes_gate"` — per CLONE, shared by every worktree,
git-ignored by pytest's own `.pytest_cache/.gitignore`, overridable by `--cache-dir` /
`HERMES_GATE_CACHE_DIR`. Files: `green.jsonl` (one line per file per green: rel, key,
record id, run id, t, seconds; compacted to the newest line per file when over 4 MiB),
`deps.jsonl` (one line per file: paths, dirs, spawned, child-covered), `runs.jsonl` (what
`.pytest_cache/hermes_bundled_runs.jsonl` is today, moved here), `durations.json` (what
`test_durations.json` is today, written from `RunLedger.file_seconds`, rel-keyed), and
`generation`. Appends are flushed per bundle so a killed run keeps its greens. **Wholesale
invalidation** happens by key for a release merge and a runner change (thousands of blobs
move; the runner fingerprint moves); by hand with `--cache-reset` (bumps `generation`).
**Opt-out:** `--no-cache` or `HERMES_GATE_CACHE=0`; a lane running `scripts/run_tests.sh
<files>` never touches the cache (the per-file runner is upstream's and unchanged).

## 2. Known reds: run once, alone, capped

**Verdict: PLAN.** A file red in the last recorded run runs ONCE, as a solo, with no re-run
alone, no straggler retry and a capped timeout.

**Decision and why.** Owner ruling O5 already says a repeat red is reported from its bundle
without a re-run — but only when the failing set is IDENTICAL, and only when a record
exists, which it never does for a landing (§0: the record dies with the worktree). On
2026-10-10 the 26 red files cost 1,405 s on their final attempt and roughly three times that
across attempts, and 13 of them were retried serially in the idle tail because a file whose
collection errors prints no summary parses as "no tests ran", which
`_is_retryable_timeout_result` reads as a timeout. Three changes close it: the record
persists (stage 1 of §1 moves it to the store), a known red is a SOLO (so its red cannot
trigger `members_to_rerun` for its neighbours, cannot kill a bundle through pytest-timeout's
thread method, and is final on its own exit), and the straggler rule skips known reds.
A known red's failing set may change: it is still reported from its one run, with
`failing set changed: +ids −ids` printed, and the record updated — a NEW red (a file not in
the record) keeps today's full path (bundle → re-run alone → leak diagnosis), because that
is the isolation-leak instrument.

**The timeout cap.** `known_red_timeout(rel, durations, flat) = min(flat, max(60, 2 ×
durations[rel]))` when the file has a cached GREEN duration (`durations` holds only clean
passes, `_clean_pass_durations`), else `min(flat, 120)`. `tests/ci/test_update_ci_routing.py`
(no green on this box) runs 120 s once instead of 300 s twice; `test_tui_gateway_server.py`
(green at ~240 s on 2026-10-05) keeps 300 s. A fixed file that now takes longer than its cap
reds by timeout, which prints `known-red timeout cap <N>s; run alone: scripts/run_tests.sh
<rel>`, and that run's green duration lifts the cap next time.

**Files and symbols.** Fork-owned.
- `scripts/run_tests_bundled_plan.py`: `known_red_timeout`; `load_known_reds` returns the
  record's `red` map plus `timed_out: set[str]` (files whose last attempt was a timeout —
  `rc == 124` or the timeout banner); `record_run` writes `timed_out`.
- `scripts/run_tests_bundled.py`: `assign_bundles` gains `known_red: Iterable[str]` → those
  files are solos; `run._solo` takes `via="known-red"` with `retries=0` and the capped
  timeout; `_retry_timeout_stragglers` skips `via == "known-red"`; the known-red solo's
  output is `_known_red_output` with the set diff. `is_known_red` (the bundle-side rule)
  stays for the case where a red file is not yet in the record at planning time but is at
  tally time (a run of two batches sharing a store).
- `Running the tests.md` § "A red is not paid for twice": the new shape (solo, once, cap).

**Stages.**
1. Persisted record (lands with §1 stage 2's store; this stage is the `timed_out` field and
   `known_red_timeout`). Test: a record with a 300 s timeout for file X and no green duration
   → cap 120; a file with green 90 s → cap 180; a file with green 200 s → cap 300. Killing
   mutation: drop the `min(flat, …)` → the 200 s file gets 400, red.
2. Known reds as solos, no retry, no straggler. Tests over `run` with fake runners: (a) a
   known-red file never appears in a bundle and its solo runner is called with `retries=0`
   and the cap; (b) a known-red solo that exits 124 is NOT in the straggler pass; (c) a
   known red whose failing set changed prints the diff and the record carries the new set;

**Size.** S: ≈ 60 runner lines, ≈ 25 plan lines, ≈ 120 test lines.

**Risks.** A red that is a load-induced timeout and would pass alone at full time is now

**Owner question.** Q5 (cap values) — §8.

## 3. Sharding slow files by node id

**Verdict: PLAN, conditional** — on by the planner's tail-bound test, never on a cold run.

**Decision and why.** §0's LPT packing says a cold whole-tree run is work-bound: sharding
its slow files moves the makespan by +1 to +3 % (repeated collection) at 8, 12 and 16
workers. Sharding earns its cost exactly when the run is small: a warm-cache run is ~26
reds plus a ~130-file audit sample, whose makespan is the single longest file
(`test_tui_gateway_server.py` 269 s, `test_run_agent.py` 292 s), and a landing gate after
§1 runs a few hundred files with the same shape. The planner therefore shards only when
`Σ estimates / jobs < 2 × max estimate` (the run is tail-bound), and only files whose cached
duration is ≥ 90 s and whose recorded test count is ≥ 2k, into `k = min(4, ceil(duration /
45))` shards. On 2026-10-10's tail: 47 files ≥ 90 s (6,904 s, 3,351 tests, median 35
tests per file), so a tail-bound run's floor drops from ~290 s to ~90 s plus one collection
per shard. Known reds are NOT sharded (they run once, whole, so their failing set stays
comparable with the record). The shard rule is a stable hash of the node id inside a tiny
plugin, not a precomputed node list: a new test lands in exactly one shard, parametrised ids
split, and module/class fixtures run once per shard (the cost that bounds k).

**Files and symbols.** Fork-owned.
- `scripts/_bundle_plugin/hermes_shard.py` (new, generic): `--hermes-shard=i/k`;
  `pytest_collection_modifyitems` deselects items with `zlib.crc32(nodeid.encode()) % k != i`
  (`config.hook.pytest_deselected`); an all-deselected shard exits 5, which the runner reads
  as a pass (today's rule).

## 4. Workers: a protocol for 8 / 12 / 16

**Verdict: PLAN (a measurement protocol with a decision rule; no number is chosen here).**

**Decision and why.** The ruled 8 (`Running the tests.md`: "12 measured slower and
load-flaked") was measured 2026-09-01 in per-file mode (1,089 processes, ~6 s start-up each);
suite-speed §1.2 re-took a 48-file median sample under the bundled runner and found 12 still
scaling but could not load 12 workers from 8 bundles. The box is 8 physical / 16 logical
cores, 32 GB. §0's packing floor is 4,694 → 3,130 → 2,347 s at 8 / 12 / 16 IF the work is
CPU-bound and scales across SMT siblings — it is not purely: classes A/C hold sockets, SQLite
WAL files and child processes, and the one known 12-worker flake
(`test_work_service.py::test_concurrent_retry_admits_one_native_task`, fork-hygiene row) is a
wall-clock admission window. The protocol measures the three things that decide it: wall,
the failure SET, and saturation; it runs AFTER §2 lands (so the serial retry tail does not
pollute the wall) and on an idle box (the same `busy_processes` check `run_tests_idle.sh`
makes), on a fixed sample that is heavy enough to load 16 workers and contains the classes
that flake.

**The protocol.**
- Sample S = the 91 files ≥ 60 s in the 2026-10-10 record (10,179 s, 5,175 tests; they are
  the A/C-class population) + 200 files drawn from the 0.5–4 s median population by
  `random.Random(7)` over the record (the fixed seed is the sample's identity); S is written
  to `scripts/worker_protocol_sample.txt` by the lane and run with `--no-cache --file-retries 0`.
- Runs: 8, 12, 16, 8, 12, 16 (two of each, interleaved so drift is visible), each
  `scripts/run_tests_bundled.sh --no-cache --file-retries 0 -j <W> $(cat
  scripts/worker_protocol_sample.txt)`, box idle, nothing else running, in the background with
  a log and the exit code unpiped. ≈ 6 × 20 min.
- Receipts per run, in the ledger (new fields in `RunLedger.summary`): `cpu_busy_pct` (mean
  and p90 of system-wide `psutil.cpu_percent(interval=5)` sampled by a runner thread),
  `mem_peak_pct`, the red node set, FLAKY and leak counts, `floor_seconds / elapsed`.
- **Decision rule.** Take the largest W such that: wall at W is ≥ 10 % below wall at the next
  smaller W on BOTH runs; the red node set at W equals the 8-worker set on both runs;
  new FLAKY or leak files at W number ≤ 2 and each is filed as a fork-hygiene row (a load
  flake is a test defect to fix, not a veto, unless there are more than two); `cpu_busy_pct`
  mean at W is < 92 % (a saturated box starves the GIL-hog class, D3.01's lesson). Otherwise
  8 stands. The chosen W becomes `scripts/run_tests_bundled.sh`'s default (a `HERMES_TEST_WORKERS`
  export before it sources `run_tests.sh`; upstream's `_adaptive_default_jobs` is untouched)
  and the ruled line in `Running the tests.md` is replaced by the receipt.

**Files and symbols.** Fork-owned: `scripts/run_tests_bundled_plan.py::RunLedger` (the
saturation sampler, `psutil` is in the test venv), `scripts/worker_protocol_sample.txt`,
`scripts/run_tests_bundled.sh` (the default export), `Running the tests.md`. Test: the
sampler thread records ≥ 1 sample per 5 s of a fake 12 s run and stops with the run; killing
mutation: never join the thread → the test's "stopped" assertion reds.

**Stages.** 1. Sampler + sample file (S). 2. The six runs and the receipt table in this
plan's §7 (a measurement lane, after §2 lands). 3. The default, if the rule picks one.

**Size.** S: ≈ 40 ledger lines, 6 runs of ~20 min on an idle box.

**Risks.** The idle-box requirement serialises this behind every other lane; the protocol
is six runs, not a sweep, for that reason. SMT scaling may make 16 equal to 12; the rule's
"≥ 10 % better than the next smaller" handles that honestly (then 12 wins or 8 stands).

**Owner question.** Q4 (the thresholds) — §8.

## 5. The fork hunks in upstream `tests/conftest.py`, and what a plugin-chain edit reaches

**Verdict: PLAN for the scope rule; KEEP for both hunks, with the reason.**

**The two hunks** (`git diff v0.21.6 HEAD -- tests/conftest.py`, 10 + / 10 −):
- (a) the stale-lock sweep: upstream's import-time block under `if not
  HOST_LOCK_DIR_AT_CONFTEST_IMPORT:` probes sibling PIDs with `os.kill(pid, 0)`; the fork
  calls `tests/_fixtures/gateway_lock_dirs.sweep_stale_lock_dirs` (psutil) instead, because
  on Windows signal 0 is `CTRL_C_EVENT` to a live sibling's console group (ledger row
  PR #131905). **It cannot move.** The fork root `conftest.py` imports before
  `tests/conftest.py` and could run the sweep and preset `HERMES_GATEWAY_LOCK_DIR` — but
  upstream's PER-TEST branch in `_hermetic_environment` (`if not
  HOST_LOCK_DIR_AT_CONFTEST_IMPORT:` → each test gets `tmp_path / "gateway-locks"`) reads
  the same constant and would stop isolating tests from each other inside a process; the
  only way back is writing that upstream module global from the plugin, which is the
  `_private`-reach weakness the fork's bar names. The brief's destination,
  `tests/_downstream/conftest_plugin.py`, registers AFTER `tests/conftest.py` imports
  (`conftest.py::pytest_plugin_registered`), so it is too late for an import-time block in
  any case. The hunk stays as the carried PR (upstream-shaped already).
- (b) the `real_hermes_root_candidates()` door (L7.06, HELD PR candidate): six additive
  lines so the plugin reads the home-I/O guard's root list through a public name. The
  alternative is reading `_REAL_HERMES_ROOT_CANDIDATES` off the module object the root
  conftest already hands over (`tests/_downstream/__init__.py::root_conftest`) — the private
  reach the door was added to retire. Keep the door; open the PR.

**What it cost, and why that was correct.** The 2026-10-10 gate ran the whole tree because
(b) changed, and `select_scope` reached every upstream file under `tests/`. That is the
right answer: a root-conftest change can change every test's fixtures. The cost is paid once
per hunk CHANGE (the next landing's `origin/main...HEAD` no longer contains it), and under §1
the same whole-tree run happens by key (every file's record names `tests/conftest.py`), so
the cache changes nothing here except the price of the run (§7).

**The current scope rule under-selects the rest of the chain.** `select_scope` computes
`changed_conftest_dirs` from `rel.endswith("/conftest.py")`. So: the fork root `conftest.py`
(no slash before it) reaches NOTHING upstream; `tests/_downstream/conftest_plugin.py`,
`tests/_downstream/*_conftest.py`, `tests/_downstream/id_markers/*`, `tests/_fixtures/*`
(imported by `tests/conftest.py` at import time), `scripts/_bundle_plugin/*`,
`pyproject.toml` (`addopts`, markers) reach only the fork files and any upstream file that
imports them by name, which is none. Each of those is loaded by EVERY test process. A
conftest_plugin edit today runs 965 fork files and zero of the 5,457 upstream files whose
autouse fixtures it changed. The rule is a spelling test: it proves "a path ends in
conftest.py", not "this module is in every session".

**Decision.** (1) The static rule gains a SESSION CHAIN list — paths and prefixes that every
test process loads — and a change to any of them reaches every file, like a conftest above
it: `conftest.py`, `tests/conftest.py`, `tests/_downstream/`, `tests/_fixtures/`,
`scripts/_bundle_plugin/`, `pyproject.toml`, `requirements-fork-dev.txt`. The root
`conftest.py` spelling bug is fixed by the same list. (2) Under §1 the list is redundant for
files with a record (the chain is in every record); it stays as the rule for files WITHOUT
a record (a first run, a reset store) and as the printed reason (`chain: tests/_downstream/
conftest_plugin.py`) so a landing knows why it is paying the tree. (3) Yes, a plugin-chain
edit should reach everything — it does change everything. The price is §7's whole-tree
number; the operational answer is batching: chain edits land in the release-merge batch,
which pays the whole tree anyway (D3.07's `--since-merge` leaves out only a conftest whose
hunk the merge did NOT change). The brief's alternative — fork files plus a stratified
upstream sample for chain edits — is a bet with no audit behind it; Q3 puts it to the owner
with the recommendation to decline.

**Files and symbols.** Fork-owned: `scripts/run_tests_bundled_scope.py`: `SESSION_CHAIN:
tuple[str, ...]`, `chain_changed(changed) -> list[str]`, `select_scope` gains the
`chain` reason bucket (`ScopeSelection.chain`), `select_for_run` prints it; `merge_change`
applies `conftest_hunk_unchanged` to every chain path that is an upstream file (today only
`tests/conftest.py` is). Test `tests/scripts/test_run_tests_bundled_scope_chain.py`: a
changed `conftest.py` (root), a changed `tests/_downstream/conftest_plugin.py` and a
changed `pyproject.toml` each reach an upstream file in a scratch tree; a changed
`tests/_downstream/README.md` does not (the list is of modules and config, `.md` excluded).
Killing mutation: keep only the `/conftest.py` suffix rule → the root-conftest arm reds.

**Stages.** 1. The chain rule + test (S, ≈ 30 lines + ≈ 60 test lines). 2. Open the
PR for (b) from the ledger row (the footprint lane's business, not this plan's).

**Risks.** A chain edit becomes a visible whole-tree run where today it was a silent

## 6. `scripts/classify_reds_on_tag.py` — red on the pure tag?

**Verdict: PLAN.** Given failing node ids and a tag, run their files in a detached tag
worktree and emit the rows a release merge classifies by hand today (`Merging upstream.md`
steps 5b/5c; `tests/_downstream/id_markers/upstream_reds_v0216.py` was hand-built from the
2026-10-10 merge).

**Decision and why.** A red on the fork's main is one of: red on the pure tag (upstream's
own — a strict `_up_red` row in `upstream_reds_<tag>.py`, or a skip-list row when the whole
file fails at collection), green on the tag (fork-caused, or a flake), nondeterministic on the
tag (a skip-list `upstream:` row, never a strict xfail — `test_update_completion_process.py`
XPASSed randomly as strict rows), or absent on the tag (a fork test, or a renamed node: not
classifiable here). The tag worktree has no fork conftest, so it IS the pure upstream
behaviour. The authority for "red" is `scripts/run_tests.sh` (one file per process); the
classifier drives upstream's `run_tests.sh` as checked out AT THE TAG, never re-spelling
the hermetic environment, and reads node outcomes from the per-file output the runner
prints for red files (`FAILED <nodeid>` / `ERROR <nodeid>` short-summary lines; a file that
passes on the tag prints no node lines, and all of its main-red nodes are then "green on
tag"). Node presence on the tag is checked with `python -m pytest --collect-only -q <file>`
through the same `run_tests.sh` (exit 0/5 and the printed ids), so a renamed test is
"absent", not "green".

**Files and symbols.** Fork-owned: `scripts/classify_reds_on_tag.py` (new, ≈ 220 lines):
