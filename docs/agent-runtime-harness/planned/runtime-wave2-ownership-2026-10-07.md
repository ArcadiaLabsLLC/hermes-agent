## R010 — pending: request-owned registrar cancellation acknowledgement

Current owner: agent_runtime/mcp_admission/registration.py::Admission.register_bounded/_work; actual registrar tools/mcp_tool_discovery.py::register_mcp_servers/_run_discovery_pass and tools/mcp_tool_loop.py. abandon ends the caller wait, but the worker owns/relinquishes _ADMISSION_LOCK only in its finally. This correctly prevents overlapping registry writers.

Control test_r010_abandon_stops_registrar_before_next_admission uses an isolated injected blocked registrar. Caller returns without done acknowledgement; next admission reports mcp_admission_lane_busy; releasing the registrar permits a late write and then the third admission progresses. Desired acknowledged stop/no late writes fails. Worker joined through done; no worker/lock leaked. There is no production MCP server in this probe.

Public register_mcp_servers takes only a server mapping, returns tool names, has no registration handle or request-owned stop/join. Generic tools.interrupt is insufficient: discovery clears stale interrupts and the interruption handler explicitly says attempts may still be running. Cancelling a Future alone does not acknowledge no future writes. Global disconnect/shutdown would affect unrelated warm/adopted servers.

Proposed upstream API, owner tools/mcp_tool_discovery.py (operation handle) and tools/mcp_tool_loop.py (loop-side cancellation): start_mcp_registration(servers, registry_scope, cancel_event=None) -> McpRegistrationTask. Handle request_cancel() is idempotent/nonblocking; wait_stopped(timeout) -> bool acknowledges ALL operation tasks/callbacks stopped and no later registry writes; result() -> RegistrationResult(status completed/cancelled/failed, tool_names, owned_spawn_ids, error). Capture the exact operation/scope, do not infer by thread or server display name. Operation tracks every spawned task and delayed callback; cancellation drains owned tasks and reaps only newly owned spawns, removes only its partial registrations, preserves prior live/adopted connections. Publish operations check cancellation under the same registry publication ownership boundary.

Fork caller: Admission owns handle and its worker. Abandon or budget expiry requests cancel; retain admission mutex until wait_stopped and worker join acknowledge quiescence. If stop budget expires, return typed cancellation_pending and keep mutex with draining owner; do not claim cancelled. Only acknowledged stopped cancellation allows worker finally to release. Add explicit mcp_admission_cancelled / mcp_admission_cancellation_pending outcomes without converting timed-out running work to completed. Existing callable injection retains old honest timeout semantics unless it supplies this cooperative handle.

Acceptance: block before connect, during async handshake and immediately before registry publish; cancel each; assert no writes after stop acknowledgement/mutex release; next admitted turn progresses; uncooperative task yields pending/busy and retains mutex; preserve unrelated warm server; owned child reaped; timeout and failure cleanup. Named future tests: test_cancel_ack_fences_registry_publish, test_next_admission_progresses_after_cancel_join, test_unacknowledged_cancel_retains_mutex. Candidate R010-REGISTRATION-HANDLE recorded; no PR filed.

## R034 — pending: final request tools owner and scoped pin

Current ordering at frozen base:
1. agent/turn_context.py::_refresh_mcp_tools_between_turns -> tools/mcp_tool_agent.py::refresh_agent_mcp_tools publishes and persist_agent_tool_names pins the refreshed agent.tools.
2. agent/conversation_loop.py restores/merges a session pin while building/restoring system prompt; same-code pins preserve bytes and append permitted fresh tools.
3. pre_llm_call -> eternia-harness settle_turn_tools -> reprune_turn_agent -> reapply_chat_lane_defer then permissions prune.
4. agent/turn_api_request.py builds api_kwargs, runs llm_request middleware. Harness callback again reprunes the agent; wire filter/brief/safety/cache transforms request tools; capture_final_request_tools records a first-request receipt only.
5. The existing pre_api_request lifecycle hook offers post-middleware observation through agent/api_request_hooks.py::_api_request_payload_for_hook, a sanitized {method, body} copy. It is useful for a later observational correction, but does not suppress refresh/prompt pin writers, own permission-bounded restore, expose authoritative unmodified tool bytes, or acknowledge attempted dispatch. Do not describe it as absent.
6. middleware callbacks currently all receive the original input; last returned payload wins (hermes_cli/middleware.py::_apply_request_chain). A later callback can replace the harness result. pre_api_request hook runs afterwards. Capturing inside one callback is therefore not proof of final dispatch authority.

No network request or operator DB in this test.
