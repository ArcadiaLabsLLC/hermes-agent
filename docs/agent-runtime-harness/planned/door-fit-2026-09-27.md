# Door fit — existing upstream doors against our asks (2026-09-27)

Lane DOOR-FIT, design sitting, docs only. Owner's question: "is there somewhere else in upstream's code where we could already
extract the data we need, so the PR or issue is not needed?" Fork tip `8cbad0dbd4` (`origin/main`); upstream read at
`upstream/main` = **`2f14d5e6e4`** (852 commits past the `77a799e2f9c` the plugin-fit sitting used; the diff since touches
`agent_init`, `conversation_loop`, `credential_pool`, `prompt_builder`, `system_prompt`, `turn_context`, `auth`, `main`,
`update_cmd*`, `async_delegation`, `mcp_tool_transport`, `process_registry` — none of it adds a hook or a config key an ask
below needs; every door named here also existed at `77a`). Method: for each ask, read what the CONSUMER (launcher or
`plugins/eternia-harness`) actually reads, then search the upstream tree for a hook (`hermes_cli/plugins.py::VALID_HOOKS`, 41
names, unchanged), a middleware (`VALID_MIDDLEWARE`, 4), a `PluginContext.register_*`, a hook kwarg, a config key
(`config_defaults.py`), a public function, a CLI verb or a stored row — and read the door's fire site to confirm it fires where
we need it with what we need. A same-named hook at a different point is NONE.

Verdicts. **EXISTS**: an upstream door yields the same data or behaviour today — the PR/issue can close. **PARTIAL**: one half is
served — the ask shrinks to the other half. **NONE**: no door; the ask stands. Line numbers are `upstream/main` at the hash above.
Previous sitting: `plugin-fit-2026-09-26.md` (its PLUGIN-AFTER rows are the consumers of the PRs in §1).
