## 2. The six answers

### 2.1 Which platforms first

**Telegram first, alone, in v1.** A BotFather token is a 30-second setup, long polling needs no public
URL or TLS (the headless box can sit behind NAT), inline keyboards give a native approval card, and the
Bot API is six HTTPS calls (`getMe`, `getUpdates`, `sendMessage`, `editMessageText`, `sendChatAction`,
`answerCallbackQuery`). Discord second (the fork's bundled manifests already name its toolsets; it needs a
websocket gateway session and `discord.py`, 8,890 lines upstream). Slack third (Socket Mode, `slack-bolt`).
Each later platform is one transport module behind the same `Transport` protocol (§3 M2) and one row.

`owner decision — which platforms, in what order · Recommend: Telegram only in v1; Discord when a second
is wanted; nothing else planned. One transport proves the bridge; the second proves the protocol.`

### 2.2 Wrap upstream's adapters, or own them

**Own them; wrap nothing.** Three facts decide it. (a) `BasePlatformAdapter.handle_message` is not a
transport hook: it derives upstream's session key, consults `_active_sessions`, slash commands,
`clarify_gateway` and the `SessionStore` — wrapping the adapter is wrapping upstream's session machinery,
which is the second session store. (b) The adapters reach into `GatewayRunner` by attribute
(`_message_handler.__self__`, `gateway_runner`); a fork handler object would have to impersonate a 4,000-
line runner's private surface, and every upstream release moves it. (c) ~90 % of the 8,323 lines are
upstream's product UX (streaming edits, topics, stickers, rich-mode ladders); the fork wants one text
turn in, one reply out, one approval card.

**The test-ownership consequence, stated.** Wrapping would make `plugins/platforms/telegram` and
`gateway/platforms/base.py` load-bearing again: ADR 0015's `unused` rows for 71+ upstream test files
would have to come OFF the skip list (610 s back into the gate), and every release merge would hand the
fork their reds to triage — tests for features the fork does not ship. Owning keeps ADR 0015 whole: the
upstream Telegram tests stay `unused`, the fork's tests are fork files under `tests/agent_runtime/
messaging/`, and `gateway/platforms` / `plugins/platforms` stay out of every bundle closure. The one
upstream thing reused is WORDING: the approval card imports `base_exec_approval.ea_header_text /
ea_action_labels / ea_default_reason_text` lazily (a kept, dependency-free module), so Telegram, the
launcher and upstream's own CLI say the same three things about an approval. Transport dependency:
raw Bot API over `httpx` (a base dependency; `agent/transports/httpx_client.py` is the SDK-free precedent),
not `python-telegram-bot` — the fork owns ~250 lines instead of an application framework with its own
event loop, updater and handler registry, and the phone closure gains no distribution.

`owner decision — wrap upstream adapters vs fork-owned transports · Recommend: fork-owned; ADR 0015 stays
whole, 0 upstream files touched, the upstream Telegram tests stay unused.`
`owner decision — python-telegram-bot vs raw httpx Bot API · Recommend: raw httpx; six calls, one module,
no second event-loop framework, nothing new in any closure.`

### 2.3 How an inbound platform identity binds to a persona instance + chat session

**A binding is a POINTER to the runtime.chat lane, never a session.** `agent_runtime/messaging/
bindings.py::Binding {platform, chat_id, thread_id|None, persona_instance_id, bound_by, bound_at}` is one
JSON file per chat under `<store_root>/messaging/bindings/<platform>/<digest(chat_id, thread_id)>.json`
(`paths.messaging_bindings_dir`), written only by `runtime.messaging.binding.set` (§3 M1). The SESSION is
the instance's chat root — resolved at send time exactly as a scheduled fire resolves it
(`PersonaTurnExecutor._root(instance) or _open(instance, request_id)`), so a `/new` in the launcher, a
retire, or an operator opening a different thread all move the Telegram chat with them, and a Telegram
chat never pins a root id of its own.

**Who may talk.** `Operator {platform, user_id, display, allowed_by, allowed_at}` under
`<store_root>/messaging/operators/<platform>/<user_id>.json`. Fail closed: an update from a user with no
row is dropped with ONE receipt `messaging.refused{platform, user_id, reason=unknown_operator}` and no
reply (upstream's `TELEGRAM_ALLOWED_USERS` semantic, minus the dev-only allow-all). The first operator is
allowed from the desktop (`runtime.messaging.operator.allow`), never from the platform.

**The inbound → turn path** (`agent_runtime/messaging/bridge.py::MessagingBridge.inbound(msg)`):
`Operator` check → `Binding` lookup (unbound chat: reply with the roster of `PersonaInstanceStore.
list_all()` handles and accept `/persona <display_name>` as the one platform-side command, which writes
the binding through the same `binding.set` service function) → `PersonaTurnExecutor.queue_inbound
(persona_instance_id, text, request_id=f"{platform}:{update_id}", origin={"messaging": {platform,
chat_id, thread_id, user_id, message_id}})`. `queue_inbound` is `queue_prompt` with the cmid prefix and
`requested_by` as parameters (`msg-telegram-<update_id>` / `messaging:telegram:<user_id>`): a re-delivered
update converges on the one queued entry; a busy root holds it (the operator sees the typing action and
"queued behind the current reply" once). The turn runs through `run_mission_chat_turn` like every other
queued send: same lease, journal, skills, MCP admission, terminal envelope, settle outbox, `turn_settled`
push to an attached launcher.

**The reply path.** `RunnerPolicy.on_settle` stays one callable; `PersonaTurnExecutor.settled` gains an
ORIGIN-KIND TABLE (`_ORIGIN_LISTENERS: dict[str, Callable]`, keys `work`, `goal`, `messaging`) in place of
its `origin.get("work")` ladder, and the bridge registers `messaging` → `MessagingBridge.settled(entry,
exit_code, payload)`, which sends `payload["reply"]` (chunked at the platform's limit, 4,096 for Telegram)
to the origin's chat and thread, and a typed one-liner for a refusal class (`chat_turn_settles.
outcome_from_payload(payload).refusal_class`). Nothing is read from history; the settle carries the reply.

**Direct turns on a bound root.** A reply the operator triggered from the launcher is NOT mirrored to
Telegram in v1 (the operator is at the desk). Approvals ARE (2.5): that is the off-desktop case.

`owner decision — one chat ↔ one instance, or a chat that addresses several personas by handle ·
Recommend: one instance per chat/thread, `/persona` to rebind; a Telegram forum topic per persona gives
"several" without a routing grammar in message text.`

### 2.4 Where platform credentials live

**In the serve head profile's Hermes-owned store, one file, through the host-store seam.**
`agent_runtime/messaging/credentials.py` reads and writes `<get_hermes_head_home()>/messaging/
credentials.json` (`{"telegram": {"bot_token": "...", "set_at": ...}}`) through `secret_files.view()` /
`secret_files.write_json()` — unbound (full Hermes) it is the plaintext file under the profile; bound
(`auth.os_secure_store`) it is the slot `hermes/v1/<profile>/messaging/credentials.json`, DPAPI/Keychain,
and a plaintext file left at the path is unlinked, exactly as the provider stores behave. Reader: ONE
function `bot_token(platform) -> str | None`; the token is never on an RPC reply, a receipt or a log
(`messaging.status` says `credential: present|absent`). An env override `HERMES_MESSAGING_TELEGRAM_TOKEN`
is honoured for a headless box provisioned by a secret manager, read through the profile secret scope so
multiplexed homes never leak it. Writer: `runtime.messaging.credential.set {platform, token}` /
`.clear {platform}`, console tier, in `LOCAL_CONSOLE_METHODS` (the same membership rule as the provider
sign-in verbs: a secret write is local-console only; the lane confirms the set `runtime.provider.signin.
begin` sits in and follows it).

Why the head home and not a persona's `hermes_profile`: a bot token is a RUNTIME identity (one poller per
token — Telegram answers a second `getUpdates` with 409), personas are many and swap; provider keys stay
per persona profile as today.

`owner decision — which profile holds the bot token · Recommend: the serve head home (`profiles/base`),
one bot per runtime; a persona never carries a platform token.`

### 2.5 The process model, and approvals off-desktop

**Process model: the serve the launcher already starts, started by the OS instead.** v1 is
`hermes harness serve --ndjson --service` with NO `--parent-pid`, started by Task Scheduler (Windows), a
`systemd --user` unit or a launchd agent that the operator writes from a documented template; the serve
owns the per-root socket lock, parks on stdin EOF, keeps both socket lanes serving, and ends on
`harness serve connect --drain`. The bridge is a serve lane: `queued_turns.start_serve_work_engine` calls
`messaging.serve_lane.start_messaging_bridge(session)` after the scheduler; it reads `messaging_enabled`,
`bot_token`, builds the transport, registers the settle listener and the approval notifier, and stops on
`session.liveness_stop` (`drain_state is not None` → stop polling, finish in-flight sends, acknowledge no
new update). A launcher that later attaches to this runtime (09 § The runtime outlives the launcher) sees
the messaging turns as `running_work` rows of kind `messaging_turn` (one `_COLLECTORS` row, the
`scheduled_turn` precedent) and the same chat history, because they are the same chat roots. An OS
service installer (`hermes harness service install|uninstall|status`, fork-owned, three OS arms) is M7,
not v1 — ADR 0015 retires upstream's; the fork's is written once the headless loop has run live.

**Approvals reach the operator wherever a bound root is.** `session_controls` gains
`approval_notifiers: dict[str, Callable[[dict], None]]` with `register_approval_notifier(session_id, cb)`
/ `unregister`; `session_approval_scope` registers the table's entry for the root when one exists, else
today's `lambda _: None`. The bridge registers a notifier for EVERY bound root at start and on every
`binding.set`, so an exec approval raised by ANY turn on that root — a Telegram turn, a launcher turn
while the operator walked away, a scheduled fire — renders as a Telegram message with an inline keyboard:
the `ea_header_text` line, the fenced command, the reason, the deadline line, and four buttons from
`ea_action_labels` with `callback_data = f"ap:{approval_id}:{choice}"`. A button press →
`respond_operator_approval({"session_id": root, "approval_id": id, "choice": choice})` — the SAME
function the launcher's `runtime.operator.conversation.approval.respond` calls, so one resolve path; the
card is edited to "approved (once) by <display>" / "denied"; an `approval_expired` refusal edits it to the
timed-out notice (`approval_timed_out_notice`). A press from a user who is not an `Operator` is answered
with `answerCallbackQuery` "not allowed" and dropped with a receipt. Only approval cards, never turn text,
are mirrored for turns the operator did not send from Telegram (2.3).

`owner decision — approval cards for turns not sent from Telegram (launcher turns, scheduled fires) ·
Recommend: yes, for every bound root; that is what "off-desktop" buys, and the resolve path is the one the
launcher uses.`
`owner decision — v1 service model: documented OS-scheduler template vs a fork `harness service install`
command · Recommend: template in v1 (M5 ships three files under `docs/agent-runtime-harness/reference/
service/`); the installer is M7 after one live week.`

### 2.6 Which bundle profile turns it on

**A harness setting, default off; no bundle manifest changes its value.** `messaging_enabled` (bool,
default `false`) and `messaging_default_persona` (string, optional) are declared in `plugins/eternia-harness/
plugin.yaml config_schema` and read through `harness_setting`. Full Hermes (a checkout, no manifest) turns
it on with `hermes config set plugins.entries.eternia-harness.settings.messaging_enabled true` or
`runtime.messaging.platform.enable`. `bundled-desktop.yaml` and `bundled-phone.yaml` add
`agent_runtime.messaging` to `switched_off_modules` (the bridge is absent from both closures, as
`gateway.platforms` is), and their `config:` blocks add NOTHING — off is the default, and a manifest row
that sets a default is a row somebody later deletes as redundant. A third manifest `headless-service.yaml`
(roots: the serve entry; `messaging_enabled: true`; the shell family present-but-off; no speech packs) is
the product the OS-service installer ships (M7); until then "turned on" means a checkout with the setting.

`owner decision — a third bundle profile (`headless-service.yaml`) now or with the installer · Recommend:
with the installer (M7); v1 proves the loop on a checkout.`

## 4. Invariants the build must keep (each pinned by a test above)

1. A messaging binding points at an instance; the session is always the instance's current chat root.
2. Every inbound is a queued send (`chat_root_send_queue`), never a direct turn; idempotent by update id.
3. One approval resolve path (`respond_operator_approval`); one wording source (`base_exec_approval`).
4. The bot token is a profile secret behind the host-store seam; it is never on a reply, a receipt or a log.
5. Unknown platform users are dropped fail-closed with one receipt; the first operator is allowed from
   the desktop.
6. The bridge is a serve lane: starts with the Work engine, stops on the drain, absent from every bundle
   closure, off by default everywhere.
7. Zero upstream files edited; the upstream Telegram tests stay `unused` (ADR 0015).

  settings, verbs, manifest pin; A2 transport + fake Bot API). Light lanes; each runs only its own test
  files. One batched landing, one gate.

  bridge); ends with the owner's first live sitting (M3 then M4 on the same token).

  landing gate.
