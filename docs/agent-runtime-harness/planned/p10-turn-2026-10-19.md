## 1. `RT-TURN-LEFT-BEHIND-RECORD` — a typed record of what a turn left behind

### 1.1 What is true today

- Upstream `agent/turn_summary.py::TurnSummaryCollector.record_tool` tallies a turn from the CLI's
  tool-progress feed ("edited 2 files +18 -3"); it SKIPS failed calls by design and is CLI display only.
  Nothing in the runtime reads it.
- Upstream emits one terminal `post_tool_call` per tool call from
  `model_tools.py::_emit_post_tool_call_hook` with `tool_name, args, result, task_id, session_id,
  tool_call_id, turn_id, api_request_id, duration_ms, status, error_type, error_message`. The terminal
  tool's `result` is a JSON string `{output, exit_code, error, status}` (`tools/terminal_tool.py::_error_json`
  is the envelope's one spelling); `write_file` / `patch` carry `args["path"]`.
- Tool calls run on `tools/daemon_pool.py::DaemonThreadPoolExecutor`, whose `submit` wraps every call in
  `contextvars.copy_context().run` — a `ContextVar` bound around `run_conversation` IS visible inside the
  hook. That is exactly how `agent_runtime/usage_ledger.py::bind_usage_ledger` already feeds the plugin's
  `post_api_request` hook (`plugins/eternia-harness/__init__.py::record_usage_ledger_row`), bound in
  `agent_runtime/profile_runner/execute.py::_run_conversation_with_usage_ledger` and copied onto
  `profile_runner/models.py::ChatResult.usage_ledger` by `profile_runner/runner.py`.
- The turn's durable record is written by `hermes_cli/harness_parts/persona/chat_turn_commit/settle.py::_project`
  through `agent_runtime/mission_chat_turns/journal.py::transition_mission_chat_turn` with a `metadata`
  dict that `mission_chat_turns/records.py::_safe_journal_metadata` whitelists block by block
  (`phases`, `run_budget`, `profile_timing`, the reasoning counts). Absent stays absent; the record's
  `TURN_RECORD_SCHEMA_VERSION` is 3 (`agent_runtime/mission_chat_phases.py`).
- `runtime.operator.conversation.read` (`agent_runtime/serve_rpc/operator_conversation.py::read` →
  `agent_runtime/operator_conversation.py::read_operator_conversation`) answers the history rows
  (`existing_persona_chat_messages`, whose agent rows carry the journal's `run_budget` block through
  `agent_runtime/persona_chat_history/markers.py::_carry_run_budget`) plus `executions[]`, one
  `agent_runtime/operator_execution.py::execution_status` per in-flight or requested turn, which already
  projects the record's `phases` through `mission_chat_phases.py::turn_timing_block` ("copies — never
  derives").
- The turn's elements already carry per-tool `command`, `exit_code`, `status`, `files`
  (`records.py::_tool_fields`), so the record could be derived at read time — but the ruling puts the
  derivation in a hook, and a read-time derivation would re-run on every history read.

### 1.2 Decision

**A contextvar-bound fold fed by the plugin's `post_tool_call` hook, classified by a table, copied onto
`ChatResult`, persisted as ONE optional block `turn_outcome` on the terminal journal record, and projected
(copied, never derived) onto the history row and `execution_status`.** Mirror of `usage_ledger` end to end;
no upstream edit (the hook name is in `VALID_HOOKS`; the executor is untouched). Failed calls are
INCLUDED — a red test is the thing a turn left behind. The Codex app-server path never fires
`post_tool_call` (same hole `usage_ledger` documents); its record is absent, which is the truth about it.

`owner decision — the 2026-10-15 deferral of this row still stands; build it on this wave? · Recommend:
yes — the two things the NEEDS PLAN line owed before exec are now supplied here (the launcher fold-summary
row is written in §7 verbatim, and the hook path was ruled 2026-10-10), and the lane is fork-only.`

### 1.3 The record (wire and store shape, identical)

```
turn_outcome: {
  "schema": 1,
  "tests":   [{"command": str≤400, "exit_code": int|null, "verdict": "passed"|"failed"|"unknown"}],  # ≤32
  "commits": [{"command": str≤400, "sha": str|null, "pushed": true|null}],                          # ≤16
  "files":   [{"path": str≤400, "op": "write"|"patch"}],                                            # ≤64, deduped by (path, op)
  "truncated": bool                                                                                  # a cap was hit
}
```

- `verdict`: `exit_code == 0` → `passed`; non-zero → `failed`; `exit_code` null (yielded to background,
  timed out without a code) → `unknown`. Never inferred from output text.
- `sha`: git's own `[<branch> <sha>]` line in the commit's output, else null. `pushed`: `true` when a
  `push` shape with exit 0 ran LATER in the same turn; otherwise `null` — never `false`, because the fold
  cannot prove a push did not happen elsewhere.
- `files`: from `write_file` / `patch` args when `status == "ok"`; `read_file` is not "left behind";
  edits made through the terminal are not inferred (honest absence).
- Bounds are `agent_runtime/running_work/rows.py::bounded_operator_text` on every string; the block is
  bounded again on the way into the store (`safe_turn_outcome`, §1.4 S4), the same belt-and-braces the
  todo checklist has.

### 1.4 Stages

**S1 — the fold** (`agent_runtime/turn_outcome.py`, new, `__layer__ = "policy"`).
`CommandKind(StrEnum) {TEST, COMMIT, PUSH}`; `CommandShape(kind, pattern)`; `COMMAND_SHAPES: tuple[CommandShape, ...]`
— the table, in precedence order (push before commit, because `git commit && git push` is one command
and the LAST shape in the line is what the operator cares about; a line matching both yields one PUSH row
and one COMMIT row). Patterns: TEST `\b(pytest|run_tests(_bundled)?\.sh|flutter test|dart test|npm test|pnpm test|go test|cargo test|dotnet test)\b`;
COMMIT `\bgit\b[^|;&]*\bcommit\b`; PUSH `\bgit\b[^|;&]*\bpush\b`. `classify_command(text) -> tuple[CommandKind, ...]`
walks the table; NO `if kind == …` ladder anywhere downstream — each kind names its own row builder in a
dict. `bind_turn_outcome()` (contextmanager yielding a `TurnOutcomeFold`); `on_post_tool_call(tool_name=None,
args=None, result=None, status=None, **_)` — no-op when nothing is bound; terminal results parsed with
`json.loads(strict=False)` guarded exactly as `agent/turn_summary.py::_extract_line_deltas` does;
`TurnOutcomeFold.block() -> dict | None` (None when nothing was folded — absent stays absent).

**S2 — the binding.** `profile_runner/execute.py::_run_conversation_with_usage_ledger` adds
`bind_turn_outcome() as outcome` to its `with` and sets `raw_result["turn_outcome"] = outcome.block()`;
`profile_runner/runner.py` copies it onto `ChatResult.turn_outcome: dict[str, Any] | None = None`
(`profile_runner/models.py`). `plugins/eternia-harness/__init__.py::register` adds
`ctx.register_hook("post_tool_call", record_turn_outcome)` with the lazy-import body the other hooks use.
`agent_runtime/first_turn_warmup.py`'s preloaded-module list gains `agent_runtime.turn_outcome` beside
`agent_runtime.usage_ledger`.

**S3 — the terminal record.** `chat_turn_commit/settle.py::_project` adds `TURN_OUTCOME_KEY:
self.chat_result.turn_outcome` to the terminal `metadata` when it is not None; `records.py` gains
`TURN_OUTCOME_KEY = "turn_outcome"` and `safe_turn_outcome(value) -> dict | None` (drops what it cannot
read, re-applies the caps, never defaults) and one more `if … is not None: result[KEY] = …` line in
`_safe_journal_metadata`. No schema bump: the phases block bumped to v3 because it changed what a v2
reader could assume; an optional block whose absence means "not recorded" changes nothing a reader
assumes (state the reason in the constant's comment). The log receipt, at settle:
`logger.info("turn_outcome turn=%s tests=%d failed=%d commits=%d pushed=%d files=%d truncated=%s", …)`
under the settle module's logger — a grep-able line, never a key on the terminal frame.

**S4 — the reads.** `operator_execution.py::execution_status` adds `"left_behind": turn_outcome_block(record)`
beside `timing` (same gating: the journal record must match `client_message_id`, `turn_id` and root);
`turn_outcome_block` lives in `turn_outcome.py` and COPIES the stored block (the bounded one).
`persona_chat_history/markers.py::_carry_turn_outcome(row, record)` beside `_carry_run_budget`, called at
the same site, so the agent row of a settled turn carries `turn_outcome` and `read_operator_conversation`'s
`history` answers the fold summary with no new verb. Doc 05 § 7 gains the block (one paragraph), doc 03
§ Existing operator conversation attachment names the two new keys.

## 2. `RT-EMIT-RUNNING-WORK-CHAT` — a fork chokepoint for terminal `running_work` rows

### 2.1 What is true today

- The chat half rides: `agent_runtime/chat_turn_presence.py::ChatTurnPresence` appends
  `persona_chat.turn_started` / `turn_ended` to the EventLog; `agent_runtime/stream/session.py::StreamSession.flush`
  asks `stream/frames.py::batch_changes_chat_turn_presence` and ships `frames.py::running_work_frame`
  (the `running_work` section alone, an overlay carrying `as_of_offset`, never a watermark) BEFORE the
  batch's own frames; the batch itself rides the `persona_chat_turn` overlay when every subscriber
  declared `patch_coverage.py::PERSONA_CHAT_TURN_CAPABILITY` (`frames.py::batch_turn_roots` requires every
  event to name a chat root). The launcher already consumes the `running_work` frame type
  (`serve_office_subscriptions.py::_NON_OFFICE_STATE_FRAME_TYPES`).
- Terminal rows are a read-time projection: `agent_runtime/running_work/lanes_process.py::TerminalLane`
  reads the `processes.json` checkpoint and `tools.process_registry.process_registry.list_sessions()`.
  Nothing appends an EventLog event when a process spawns or exits, so the hub learns of it only from the
  freshness backstop or an unrelated write — and then as a FULL core.
- Upstream `tools/process_registry.py::ProcessRegistry` has exactly two chokepoints every spawn path and
  every exit path cross: `_track_started` (called by `spawn_local`, `_spawn_local_pty`, `spawn_via_env`
  and the recovery path, after the session is in `_running` and `_write_checkpoint()` ran) and
  `_move_to_finished` (reader-observed exit, kill and reconcile all land here; "only the FIRST move
  enqueues the completion notification"; `_publish_finished` writes the checkpoint then queues the
  completion). There is no listener on either; `tools/process_registry_notifications.py` is display
  formatting, not a spawn/exit seam. Announced builds are written by the job's external writer into
  `builds.registry` records and detected by `agent_runtime/builds/sweep.py` at read time.

### 2.2 Decision

**An additive upstream seam — `ProcessRegistry.add_lifecycle_listener` fired fail-open from the two
chokepoints — a fork listener that appends a typed event pair, and the stream treating a batch made only
of those events as a `running_work` SECTION batch (the section frame carries the batch's watermark when
every subscriber declares a sixth capability token), never a core.** This is the chat half's exact
mechanism one lane over, not a keyed `state.patched`: a `state.patched running_work` row would need
`patch_coverage` to declare a new fold entity AND the launcher to fold `running_work` rows from op-based
patches (its `kMissionFoldDeclaredEntities` does not know the entity — the launcher row says so), while the
section frame is a wire the launcher already folds whole. Announced builds stay on the full-core lane
(ruled; their writer is not hermes). The keyed-patch design is recorded as the later step, taken only if
the section read is measured too slow (§2.5).

`owner decision — the listener installs from the plugin's register(ctx) (every hermes process that hosts a
ProcessRegistry) or only from the serve boot? · Recommend: the plugin — every process that writes the
checkpoint the projection reads is a writer of the row, and a CLI-run turn's background process must reach
the same subscribers; the install is idempotent and lazy.`

### 2.3 Stages

gains `self._lifecycle_listeners: list = []`; `add_lifecycle_listener(self, listener)` appends;

## 3. `RT-MISSION-CHAT-MESSAGE-TAKES` — reviewed files on the chat send, limits published

### 3.1 What is true today

- The native conversation lane already takes files: `agent_runtime/conversations/prompt.py::validate`
  admits `prompt.files: [{name, media_type, data (base64)}]` against `MAX_FILE_COUNT=8`,
  `MAX_FILE_BYTES=256 KiB`, `MAX_FILES_TOTAL_BYTES=512 KiB`, `FILE_MEDIA_TYPES` (`text/*`, json, xml,
  yaml, csv, pdf), refuses with `conversations/model.py::Refusal.FILE_UNSUPPORTED | FILE_OVERSIZE |
  FILE_INVALID`, publishes `files_capability()` on `conversations/service.py::capabilities` (v3), and
  stages bytes on the native peer (`prompt.py::_attach_file`). The launcher decodes exactly this
  (`eternia_hermes_adapter/.../native_prompt.dart::NativeFileLimits.fromCapabilities`, `kNativeFileRefusals`).
- The mission lane (`runtime.chat.message`) takes TEXT and IMAGES only: `agent_runtime/chat_turn.py::CHAT_MESSAGE_PARAMS`
  lists `images`; `normalize_chat_message` stores them content-addressed through
  `agent_runtime/operator_images.py::store_images` and lowers each to argv `--image sha256:<hex>.<ext>`
  (`chat_serve_route.py`'s route table row `("images", "--image", "list")`); `chat_turn_commit/admit.py::_admit_images`
  resolves the refs (`resolve_refs`) and refuses a model without vision; `chat_turn_commit/run.py` composes
  the persisted row with `operator_images.with_media_lines` (`MEDIA:<path>` lines) and hands
  `AgentRunRequest.user_image_paths` to the runner; the journal keeps `pending_user_images` for replay.
- Limits are published once, on the method-lane manifest: `serve_rpc/registry.py::manifest` →
  `"limits": {"operator_text": operator_message.operator_text_admission()}` — that IS the
  `rpc.limits.operator_text` the launcher reads at hello.
- The launcher console send is text-only (`agent_console_send_lane.dart::dispatchOperatorSend`); its
  plan `EterniaLauncher/docs/mission_control/planned/CONSOLE_ATTACH_FILE_2026-10-16.md` D3 shows "Attach
  file" DISABLED until limits are published, and D4 sends a `FileAttachment` in `prompt.files` shape.

### 3.2 Decision

**`runtime.chat.message` gains `files` in the native lane's exact item shape and refusal spellings; the
limits are the native lane's constants published as `limits.files` on the manifest (one owner of the
number, D2.01); files are stored content-addressed like images, lowered to argv `--file <ref>`, resolved
at admit, and reach the model as `FILE:<path>` lines beside `MEDIA:` — the agent reads them with
`read_file`.** No new RPC verb; `RPC_CONTRACT_VERSION` does not move (an additive param and an additive
limits key). The review/redaction path is the images' path: bytes never cross a door by path, the stored
file is under the store root, the persisted row names the path the way `MEDIA:` does and
`_redact_persona_chat_text` applies to the composed text as it does today.

`owner decision — inline a text file's content into the prompt, or stage it and name its path? ·
Recommend: stage + path line — 512 KiB inlined is ~130k tokens on every turn that carries it, while a
staged file costs nothing until the agent reads what it needs; it is also the one shape that keeps
PDF (unreadable inline) on the same lane.`

### 3.3 Wire shape

```
runtime.chat.message params += "files": [{"name": str≤200, "media_type": str, "data": base64}]   # ≤ limits.files
```

## 4. `RT-HARNESS-ARGV-MANIFEST-SCAN` — the declared-command scan pays a stat walk, not a parse

### 4.1 What is true today

- `hermes_cli/main.py` (upstream) calls fork-owned
  `hermes_cli/plugins_manifest_cli_commands.py::attach_declared_cli_command` for any first token not in
  `_BUILTIN_SUBCOMMANDS`; `harness` is such a token, so `discover_declared_cli_commands` runs on EVERY
  `hermes harness …` process (each CLI call, each serve boot, each test child). It calls upstream
  `hermes_cli/plugins_discovery.py::collect_directory_manifests` (bundled root minus five own-discovery
  categories, `<HERMES_HOME>/plugins`, the project dir when `HERMES_ENABLE_PROJECT_PLUGINS`), which parses
  EVERY `plugin.yaml` through `plugins_manifest.py::parse_manifest_file` (`fast_safe_load` on ruamel), then
  gates each winner with the live config (`gate_manifest`). Precedence: `winners` is a dict keyed by
  `manifest_key(m)` (`key` = `<cat>/<dir>` for category manifests, `name` FROM THE YAML for flat ones) in
  scan order, later roots overriding earlier.
- One manifest declares a command today (`plugins/eternia-harness/plugin.yaml`: `harness`, `postinstall`).

### 4.2 Measured (scratch, this lane, 2026-10-19)

In-process, `~/.venvs/hermes-test` python 3.14, `HERMES_HOME=X:/Eternia/.hermes`, worktree checkout, one
warm-up then **n = 20** timed runs each; **box load 100 % of 16 logical CPUs before and after** (other
lanes live) — every number is an upper bound, and the RATIOS are what the decision rests on.

| option | median | min | p90 | what it is |
|---|---|---|---|---|
| A `collect_directory_manifests()` | 148.9 ms | 86.5 | 175.8 | upstream walk + YAML parse of 58 manifests |
| B `discover_declared_cli_commands()` | 117.5 ms | 91.7 | 160.6 | A + config read + gate (the seam's whole cost) |
| C stat-walk, no parse | 14.5 ms | 11.2 | 23.8 | over-approximating enumerator: 103 manifest files, (path, size, mtime_ns) |
| D C + text prefilter (`b"cli_commands" in bytes`) | 28.8 ms | 22.6 | 48.7 | |
| E `parse_manifest_file` of the ONE declaring manifest | 1.5 ms | 1.3 | 2.0 | the cache-hit re-parse |
| F `load_config_readonly` + `gate_manifest` of it | 0.1 ms | 0.1 | 0.1 | the live gate |

C sees 103 files where A parses 58 because the enumerator applies no `skip_names` and caps depth one level
deeper — the superset is the point (§4.3). A cache HIT costs C + E + F ≈ 16 ms against B ≈ 118 ms, ~7× on a
loaded box; D cannot win on its own because a flat manifest's KEY is its YAML `name`, so the prefilter still
has to parse every manifest to know who the winners are, or re-implement upstream's key rule.

### 4.3 Decision

**Option (a), the fingerprint cache in `HERMES_HOME`: keyed on an over-approximating stat enumeration of
every manifest file the upstream walk could read; a hit re-parses ONLY the declaring manifest(s) and gates
them LIVE; a miss runs today's full scan and rewrites the cache.** Precedence stays identical by construction:
the winners map is a pure function of the manifest files' contents and scan order; the fingerprint covers
a superset of those files with `(path, size, mtime_ns)` and the env flags that choose the roots, so any
change the upstream walk could observe is a miss, and a hit means the declaring manifest is still the
winner it was. The enable gate is never cached: it runs on the re-parsed manifest against the live config
on every call. Option (b) is rejected above; option (c) (`harness` as a built-in verb) drops the
plugin-disable gate for it, which the row names as the cost and which `HERMES_SAFE_MODE` relies on.

On "without duplicating upstream's directory walk": the enumerator is not a second copy of
`scan_directory` — it carries none of its semantics (no parse, no key, no skip list, no portable-package
rule); it is a bounded `os.scandir` over the same three roots that answers only "which manifest files exist
and when did they change". The alternative, reusing `scan_directory` with parsing stubbed, reaches a private
name through a patch and is refused by the import-layer gate. A positive test (§4.5 T1) pins the superset
by building both sets and comparing.

### 4.4 Stages

**S1 — `hermes_cli/plugins_declared_cli_cache.py`** (new, fork-owned, keeps the cli_commands module under
the ceiling). `MANIFEST_FILE_NAMES = ("plugin.yaml", "plugin.yml", "plugin.json")`;
`manifest_fingerprint(roots, *, depth_cap=2) -> Fingerprint` (frozen: `schema`, `roots`, `env`
(`HERMES_ENABLE_PROJECT_PLUGINS`), `files: tuple[(path, size, mtime_ns)]` sorted); `CACHE_RELPATH =
"cache/declared_cli_commands.json"`; `read_cache(home) -> CachedRows | None` (any malformed or
schema-mismatched file → None, debug receipt); `write_cache(home, fingerprint, rows)` — temp file +
`os.replace`, failure logged at debug and ignored (a cache that cannot be written is a cache that always
misses, never a broken CLI). A cached row is the descriptor minus its callables plus `manifest_path`,
`source`, `prefix`, `plugin_key`.

**S2 — `plugins_manifest_cli_commands.py::discover_declared_cli_commands`.** Safe mode → `[]` (before any
I/O, as today). Compute the fingerprint; on a hit, for each cached row: `parse_manifest_file(manifest_path,
Path(manifest_path).parent, source, prefix)` (a parse that answers None → treat as a miss), `gate_manifest`
live (`load_config_readonly` once), build the same descriptor today's loop builds (the `setup_fn` closure
over the re-parsed manifest — `_materialize_declared_cli_command` is unchanged). On a miss: today's loop,
then `write_cache`. One receipt line at debug: `declared_cli_scan cache=hit|miss|unwritable files=%d ms=%d`.
The roots come from the same functions the upstream walk uses (`_plugins.get_bundled_plugins_dir()`,
`get_hermes_home() / "plugins"`, the project dir rule) read through `hermes_cli.plugins` at call time so
tests that patch them keep working.

**S3 — docs.** Doc 04 (boot): the cache, its path, and the invariant "a hit never changes which plugin
wins or whether it is enabled"; doc 11 (gate directory): T1.
